# 创艺坊图片 API 接入分析

核验日期：2026-09-23。范围：公开文档、模型广场、当前 metasocli 图片契约与登记代码。未提交生成请求、未使用密钥、未修改产品源码或业务项目。

## 结论

按供应商公开契约，可以给 metasocli 增加独立的图片 API 执行后端。保留已有资产划分、完整图片提示词、依赖关系和逐段引用；新增图片任务记录、受限并发、返回结果处理和恢复逻辑，再衔接既有资产登记。

这不是将 50 份不同提示词拼进一次请求，也不是沿用视频 task_id 轮询。该图片文档描述的是一次请求直接返回图片结果；没有公开保证 task_id、查询接口或幂等键。

## 三、实际请求契约

后台域名是 newapi.yiciyuang.com；专属文档明确给出的 API 基址是 https://api.yiciyuang.com。

### 无参考图

POST /v1/images/generations，application/json，Bearer 鉴权。

以下只展示文档格式，未执行：

```json
{
  "model": "gpt-image-2.5",
  "prompt": "这里放已经保存的完整资产图提示词",
  "quality": "medium",
  "size": "1536x1024",
  "n": 1,
  "response_format": "url"
}
```

quality 的承诺范围是 auto / low / medium / high。比例与分辨率需要映射成 size 像素尺寸。不能直接假定 ratio、resolution、xhigh、max 等字段可用，也不能把“4K”写进提示词视为输出尺寸证据。

### 有参考图

POST /v1/images/edits；专属文档支持 JSON 和 multipart/form-data。单图使用 image，多图使用 images。当前项目已有依赖资产顺序，应按该顺序传入真实图片，不能只把依赖的资产名称写进提示词。

### 响应

默认读取 data[].url；请求 b64_json 时读取对应字段。文档还列出 revised_prompt 和 usage，均需按实际是否存在记录。

不能声称这些字段每次必返，也不能把请求中的 model 当成服务端底层模型身份的证明。revised_prompt 表示供应商可能修改提示词：本地原始提示词及其哈希必须保留，返回文本另存，不能覆盖配方或谎称全链路未改写。

## 四、发现的文档不一致

1. 用户提供的通用生成/编辑页面，上方请求示例采用 input.messages / parameters，下方在线测试使用顶层 prompt。专属 GPT Image 2 / 2.5 文档明确使用后者。
2. 模型广场详情 API 示例仍使用聊天接口；参数表还出现 standard、vivid、n=1~10，与专属图片文档不同。
3. 图片总览仍写单一 gpt-image-2，但专属文档与当前模型列表均列出四个模型。

实施时应以专属文档为暂定契约，锁定小范围参数，再做授权后的真实接口验收；不能将互相冲突的示例拼成请求。

## 五、50 张不同资产图应如何执行

一个资产对应一个本地任务、一个完整提示词、一个请求，n=1。n 是同一提示词生成的张数，不代表不同提示词数，也不代表并发额度。文档说常用 n=1~4，不能据此认定该账户上限是四并发。

本地任务先保存 operationId、assetId、recipeHash、请求参数及依赖图片哈希，再提交。每个响应由发起它的任务接收并保存，不依靠返回顺序，也不要求供应商回传 assetId。

可一次建立 50 个任务，由可配置的并发队列执行：只取依赖已就绪的任务；某个请求返回并持久化后释放其请求名额，下载和登记由独立受限流程处理。有图片依赖的后续任务，要等对应图片已下载、校验和登记后才可提交。

共享资产复用现有 ID；失败或缺失只影响对应项与其依赖项。项目原有集/段引用无需根据图片结果重新猜测。

公开模型详情列出 default 的 RPM=110、RPD=1.8K；这不是最大在途请求数，也不是已验证的用户账户限额。并发上限、最长请求耗时、实际限流响应仍需供应商或账户信息确认。

## 六、中断与重复计费是关键差异

当前文档未展示异步 task_id 查询接口，也未说明幂等键。因此：

- 已拿到图片 URL 但下载失败：保存原响应，只恢复下载，不再次生成。
- 图片已落盘但登记中断：从本地文件恢复登记。
- POST 已发出但超时/连接中断：记录结果未知，不能直接判定未生成并自动重发。
- 接入时需要可配置的较长生成超时。模型广场当时显示的平均延迟约为 Image 2 的 330 秒、2.5 的 134 秒；只是动态观测值，不是 SLA，足以说明不能照搬很短的 HTTP 超时。
- 需要保留所有非敏感响应诊断信息；如果有请求追踪 ID，可保存用于对账，但不能将追踪 ID 当成可查询的生成任务 ID。

## 七、与当前 metasocli 的最小改动关系

已经存在、可保留：

- src/contracts/story.ts：稳定 assetId、完整 recipe.prompt、dependencies、每段 references、文件哈希。
- src/assets/registry.ts：按资产 ID 校验并复制图片、项目锁、原子保存和状态更新。
- src/assets/image.ts：PNG/JPEG/WebP 的技术检查及 H3 兼容尺寸约束。
- skills/metasocli-reference-images：先准备完整配方，再原样生成图片的业务顺序。

需要新增或调整：

1. 独立图片供应商配置及凭据，与 METASO_API_KEY 分开，限制凭据只发到配置的 API 目标；下载图片不携带生成 API 的认证头。
2. Node.js/TypeScript 图片请求适配器，覆盖 generations、edits、URL/Base64 返回和实际响应校验。无需自建 New API 服务，也无需改为 Python。
3. 图片任务与队列，保存请求意图、并发状态、结果未知、下载/登记恢复，必要时在同机多个项目之间共享该图片账户的并发额度。
4. 图片 Skill 和 validate_handoff.py 增加明确的 API 执行模式；当前只接受 built_in / not_run，不能将外部 API 伪装成宿主原生调用。
5. 增加离线契约、乱序完成、限流、参考图依赖、返回丢失、下载失败和登记中断测试。

登记建议先下载为项目本地文件，再走既有 registerAsset(file, provenance=imagegen)，避免将供应商可能过期的图片链接作为后续视频引用的唯一来源。

现有检查要求单图不超过 30 MiB、宽高 256~5760、宽高比 0.4~2.5。供应商列出的 1:3 / 3:1 虽可能可生成，但不符合现有 H3 参考图登记约束，不能直接开放所有比例。

图片全部就绪后再生成新的 H3 视频计划；资产登记会增加项目修订号，之前的视频计划可能过期。图片执行后端改动不要求改变 H3 视频生成接口、旁白绑定或提示词原文。

## 八、尚未验收的项目

- 账户是否有这四个模型的权限及适用计费分组。
- 最大在途并发、请求超时上限、明确的限流处理规则。
- 最大 prompt 长度、参考图片数量/格式/体积限制。
- URL 有效期、是否提供可靠的结果找回机制或幂等支持。
- 实际生成尺寸、真实中文排版效果和长期稳定性。

当前结论是公开契约与本地架构层面的可接入性；没有将文档声明写成实测成功，也没有发起付费生成。

## 九、针对当前代码的接入注意事项（追加核验）

以下是接入设计要求，不表示已经实现。追加核验只读源码、现有测试与 Skill，未发起网络生成或运行新的付费验收。

### 1. 不复用视频模型字段、任务目录和并发账本

`src/contracts/story.ts:16` 的 model 属于视频段参数，固定为 MiniMax-H3。`src/contracts/plan.ts` 的计划同样绑定 H3 视频。图片的 model、quality、size、供应商配置应放入新的图片执行计划/记录，不能把既有视频字段改成 gpt-image-2.5。

`src/jobs/store.ts:47` 会将 `.metasocli/jobs/` 中每个 JSON 按视频 Job 解析。视频 Job 的成功状态依赖 taskId、视频计划和时长输出；图片任务混入这里会破坏视频扫描与共享协调。建议为图片设置独立子目录，例如 `.metasocli/image-jobs/`，具体名称在实施时定稿。

`src/jobs/coordinator.ts:25` 的账本是 video-ledger.json，batch.lock 也属于视频调度。图片要有独立账本/锁及可配置额度。同机多个项目使用同一图片服务额度时应共同计数，不能每个项目都各自认定有完整额度。多个账户/凭据是否共享供应商上限需要显式配置，不能用更换 Key 绕过账户级限额。

### 2. 全局 revision 不能原样用作图片批次的失效条件

`src/assets/registry.ts:36` 每次有效资产登记都会增加 story.revision；`src/core/planning.ts:86` 的视频校验比较整个故事 revision 和 manifestHash。

如果复制视频计划校验实现图片队列，第一张图登记后，余下 49 张可能立即被视为过期。图片计划应验证本项目身份、本任务的资产配方、选定参数、依赖图片哈希以及目标资产是否被替换；其他独立图片的正常完成不应使整个图片批次失效。

第一版最稳定的执行顺序：完成所选范围的草稿导入、资产生成与登记，然后创建视频计划并运行视频批次。同一个故事根下，不要在运行已冻结的视频批次时继续导入后续集或登记新资产；即使新资产属于别的集，也会触发全局版本变化。不能通过放松现有视频 PLAN_STALE 检查来掩盖这个问题。已经有远端 ID 的视频恢复不应因此再次生成。

### 3. 网络并发，短状态写入串行

`registerAsset` 使用 `withProjectLock`，后者获取失败时可能直接返回 LOCK_BUSY。并发完成的图片不要同时直接启动多个登记写入，也不要在生图网络等待期间持有项目锁。

建议：网络请求并发；图片结果先单独持久化；登记通过同项目的短写队列逐项进行，跨进程使用原有文件锁；锁忙只恢复登记，不重新生图。

还要防止同一 assetId 被两个任务同时付费生成。任务应持久化提交占位，并在结果登记时核对目标仍由本任务管理、没有被用户换图。现有 registerAsset 检查配方，但不会替图片队列检查任务归属。若要增加带条件登记，应在同一次短锁内检查并写入，避免“先检查、解锁、再登记”的竞态。不要外层持项目锁后直接调用会再次加锁的 registerAsset。

### 4. 执行哈希要覆盖图片模型与真实依赖

现有 recipeHash 是原始配方对象哈希，包含资产 ID、种类、提示词、精确文字和依赖 ID，不包含图片供应商、模型、尺寸和质量。这份历史哈希不应被偷偷改变。

新增图片 requestHash/inputHash，覆盖目标供应商、接口、请求模型、完整提示词、quality、size、n、返回格式及参考图真实哈希与顺序。密钥本身不得写入计划或参与可公开日志。仅依赖 ID 相同不足以证明参考图未变化。

同一个已登记 ready 资产默认继续复用；切换默认生图服务不意味着重画旧项目全部图片。用户明确要求重画时建立新的操作记录，保留旧结果和来源。改变外貌配方仍遵守新 assetId 与显式引用更新规则。

### 5. 图片 Skill 的执行契约必须真的扩展

`validate_handoff.py:24` 只接受 built_in / not_run，成功项在第 412 行也要求 built_in。需要扩展 API 模式并保持旧记录兼容，不能将第三方执行记录伪装成原生生成。

modelPreference 当前只是说明字段；requireExactModel=true 会直接拒绝。真正指定 2.5 必须体现在实际 API 请求的 model 中。应区分“请求了哪个模型”“供应商报告哪个模型”“是否有独立身份凭证”，不能因为发出了 model 就移除原有的不可核实限制。

正文在 `skills/metasocli-reference-images/SKILL.md`，`.agents/skills/` 是转入正文的入口。普通成品提示词、旁白、剧本入口均应明确选择一次图片执行后端，避免一边跑 API、一边仍调用原生生图造成重复生成。旁白 MP3 不进入图片请求。现有首次结果保存展示、无自动审美退图/重画的规则继续保留。

### 6. 提示词和参考图应按原有完整契约提交

完整提示词原样发送，不能为适配 API 缩成摘要，也不能静默截断。项目上限是 32000 个 UTF-16 单元，供应商的实际上限尚未得到文档确认，需要在付费前尽可能校验。

无参考图片用 generations；有依赖图片用 edits，并传入明确顺序的真实图片。派生状态图或首帧不能只传“参考某个人物”文字代替依赖文件。图片依赖是资产依赖，不应无差别地把所有人物图附到每张生成请求里。

供应商返回 revised_prompt 时另存为执行事实；不覆盖原 recipe.prompt。HTTP 200 但图片数组为空、URL 无效或 Base64 不可解码时，不得伪装为成功，也不能据此自动发起第二次付费请求。

### 7. 返回结果要持久化，不能只依靠控制台日志

该供应商文档没有保证可查询 task_id。每个请求绑定本地 operationId；返回后尽早保存可恢复的结果信息。

复用视频日志脱敏函数时要注意：它会去除 URL。公开日志可以脱敏，但恢复存储需要受保护的真实结果地址或已落盘的图片；否则进程中断后只剩哈希，无法恢复下载。签名 URL 不打印到日志或聊天中。

超时/断线/进程崩溃不证明远端未执行。结果未知的任务不能自动重发、换模型或当作未占用名额来补交。可恢复已有结果的下载和登记；未提交项是否继续要服从未知占位及已授权范围。

### 8. URL、Base64 和 HTTP 限制不能照搬视频客户端

`src/metaso/client.ts:47` 当前视频 POST 超时 120 秒，`:57` JSON 响应上限 1 MiB。同步图片生成耗时可能更长；Base64 图片响应也可能明显超过 1 MiB。图片客户端应有单独、有限且可配置的生成超时与响应大小上限。

优先按文档返回 URL，再下载落盘。若支持 Base64，应同时限制响应体、Base64 解码后的字节数和并发下载/内存，不将数十张 Base64 图片塞进一个状态 JSON。

`registerAsset --url` 会保存本地副本，但 `src/metaso/h3.ts:70` 仍使用原远程 URL。为避免临时图片地址成为后续 H3 的依赖，推荐先下载为本地图片，再以 --file 登记。下载失败可重试下载；地址失效不能静默重新生图。若供应商返回重定向链，需单独验证安全下载策略，不能把认证头传给 CDN 或无条件允许任意重定向。

### 9. 资产板的比例与视频比例是两回事

人物、场景、道具模板默认是横向 16:9 设计板，包含多视图及文字信息。不能因为视频是 9:16，就给所有资产图统一传竖屏尺寸。首帧才按具体镜头构图处理；现有 H3 首帧模式不能与其他参考图或旁白混用。

专属文档明确列出 16:9 + 1K 对应 1920x1088；这属于供应商映射，不是数学上精确 16:9。其他档位也应使用经过确认的尺寸映射，保存实际返回尺寸，不凭“2K/4K”名称推断像素。

### 10. 图片能生成，不代表一定能进入当前视频请求

`src/assets/image.ts` 限制单图 30 MiB、宽高 256~5760、宽高比 0.4~2.5；每段最多九张图。供应商的部分超宽或超长比例超出项目可登记范围，第一版应限制为可用于后续 H3 的规格。

`src/metaso/h3.ts:13` 还限制整个编码后请求为 64 MiB。本地图片会转换为 Base64，体积约增加三分之一。例如九张各 6 MiB 的图，图片 Base64 本身就约 72 MiB，尚未加入提示词和旁白，单图虽合格但整段视频会拒绝提交。

因此需要根据每段的组合做总大小预检。第一版先选通过兼容验收的输出规格；若确需较大图片，应明确增加有记录的尺寸/格式派生或已配置的稳定 URL 方案，不能在最后一步偷偷压图、裁图、换图或删引用。

### 11. 密钥、调用范围和模型切换要独立

图片供应商使用独立配置与凭据，不覆盖当前 `.local/metaso-credentials.json` 或 METASO_API_KEY。API 基址采用专属文档的 api.yiciyuang.com；请求目标与鉴权绑定，下载域名不继承密钥。

图片计划/状态/导入不付费；提交命令在用户已明确授权的资产范围内运行，不逐图再次询问，也不能把视频授权自动解释为向新图片供应商上传素材的授权。当前用户请求只有分析，尚未执行任何接入或付费调用。

批次中明确固定 gpt-image-2.5，除非用户选了其他变体。失败不自动切 Image 2、Flare 或原生生图。平台别名不等于已验证的底层型号；实际效果与中文设计板排版需要后续授权验收。

### 12. 接入验收应覆盖的项目特有情形

- 50 个不同资产乱序完成，实际在途数量不超配置，并登记到正确 ID；跨集共享资产只生成一次。
- 第一张图登记后，余下图片任务继续有效；所有图就绪后创建的新 H3 计划通过，旧视频计划仍按原规则失效。
- 两张图同时完成不会因登记锁冲突触发重生图；同一资产的并发执行只允许一次付费提交。
- 用户在生成期间替换资产、或修改依赖图时，旧任务结果保留但不覆盖新选择。
- 无图依赖走 generations；有依赖走 edits，真实文件哈希和顺序完全对应；音频被排除。
- 超时、HTTP 200 空结果、429、损坏响应、结果已接收但保存中断、下载中断、登记中断均有区分；创建结果未知不自动重发。
- URL/Base64、错误文件格式、过大单图、超大 H3 组合请求、横向资产板与竖向首帧分别校验。
- 旧原生图片记录、已有视频 Job、视频四并发、旁白及 context_ir_enabled:true 行为保持兼容。

第一版建议采用“现有配方与登记 + 独立图片计划/任务/客户端/并发记录 + Skill 后端选择”。继续使用 Node.js/TypeScript 和现有文件持久化，不需要引入新数据库、消息中间件、常驻服务或改造视频模型。
