# 视频容量自动释放（R3）

2026-11-09。原 `video run`、`video execute`、`batch run/resume/retry` 和单段 `generate` 共用容量处理与派发票据。默认策略已确定，不增加确认、清理命令、额外 GET 或常驻进程。这里的规则替代早期文档中的“视频未知必须永久占位”；图片及独立 IR 不变。

| 观察到的事实 | 本地容量 | 业务记录 |
|---|---|---|
| 无 taskId，创建异常结束，或提交 owner 已退出 | released | 原 unknown、operationId、attempt、错误保留 |
| 有效 owner 尚在创建或保存回执 | held | 保护实际预留，暂缺 ID 不释放 |
| 实际 GET 失败、超时、认证失败、查不到、状态或身份不可信 | released | 原 ID 和错误保留；后续有界查询仍用原 ID |
| 外部故事移动、删除或必要任务证据无法核实 | released | 仅可信账本中对应项改变，不写外部故事 |
| 明确 queued/running，哪怕很久或本地停止 | held | 不按300/600/3600秒清理 |
| 新匹配证据证明仍活跃 | held | 重新计数；达到或超过4停止新增，保留查询和下载 |
| 身份可信且平台明确完成、失败或取消 | released | 输出URL、元数据、文件、下载校验仍独立决定交付是否成功 |

POLL_LIMIT、用户停止和容量等待预算结束不是 GET 失败。释放不是远端取消、成功或重试授权。同一项目、同一集段、同输入（inputHash）的旧未知不能换批次再 POST；一次新尝试仍使用原明确授权入口。不同集或不同段即使正文、素材与 inputHash 相同，也按各自原冻结范围授权分别处理，不改既有哈希算法。用户已修改输入并授权新冻结范围时，已释放的无关旧尝试不阻断新段；独立 IR 的未知阻断规则不变。

当前已知 held 采用本机共享上限4，项目 concurrency 为附加上限；下载独立最多2路。未知请求可能实际已受理，因此策略释放后远端真实任务数可能超过4。迟到活跃证据恢复计数后暂停新增；不能把此策略描述为远端绝对四并发保证。

正式执行首次申请容量时对 held、存在未完成观察水位，以及“以无 ID 原因释放但已有 ID”的非终态项做小文件检查，有界并行4项，一项就绪即提交决定。已应用可信终态不因尾水位反复展开检查。空位可先用，不等最慢外部目录。普通同步保留已经保存的容量决定，不凭旧 queued/running 重占。查询优先处理当前故事 held 任务，已释放的已知 ID 只使用原轮询预算内空余能力；正常工作结束后不为它另开等待预算。创建错误按项分类；当前账号/授权/输入错误停止本次派发并让出票据，历史旧错误不停止新运行。

运行票据绑定项目、冻结范围哈希、owner 和剩余派发范围，按进入次序分配真实空位。A并发4有后续段时优先补A；A并发1时多余三份可给B；A只剩两段时不虚占另外两份；最后预留到进入HTTP之间仍属于该次派发进度。待提交清空后让出优先权，不等下载；暂停/退出后恢复重新排队。票据不创建虚假任务预留。

共享 `video-ledger.json` 为唯一容量真相。schemaVersion=2 的 slot.capacity 保存 held/released、R3策略、决定版本、issued/applied观察水位、原因、证据哈希、终态和源证据指纹。`.metasocli/receipts/<operationId>-capacity.json` 是带哈希的最近观察证据，可补齐“证据已写、容量未写”的中断窗口，不是第二份容量账本。原 Story/Plan/Job/Run 身份和冻结哈希不变。

容量事件在项目锁内选定实际保留的证据，释放项目锁后才应用共享事务。身份及 taskId 匹配的可信终态，即使序号落后也能补齐，后到 running 不会复活它；重复应用不写回。Job/回执/事件与账本已有 ID 冲突，只产生可恢复的 source_unavailable，不把错误 Job 的完成状态同步成可信终态。

找回任务 ID 的成功回执经过 operationId、requestHash、项目/根及原 ID 核对后，在同一共享事务补齐 ID 和容量。register、原 submit 复用及必要的小记录审计共用这条修复路径；不扫描全部已释放历史。旧成功回执不能撤销后来查询失败或来源异常的释放；来源异常后首次发现新有效 ID 可以恢复，已知 ID 的再次恢复要有新的匹配活跃证据。较早无 ID 观察不能覆盖后来的有效回执。恢复到5个 held 如实记录，禁止新增第6个，原 ID 查询和下载继续。

只读 status/doctor、本地 video run、计划和导入不释放、不迁移、不增加网络请求。status、batch status 和正式执行交付分开显示业务结果与容量。单任务远端 status/resume/download/attach-task 只消费本操作实际证据，不查询所有项目。没有运行进程时没有后台定时清理。

升级须冷切换：先结束旧版本执行，再运行新构建。第一次写事务校验旧账本并保留不可覆盖的 `video-ledger.v1-<原hash>.json`，再保存v2；旧二进制会拒绝v2。活跃旧提交者或调度者、无法识别的锁均不强制删除。只读命令可读v1且不迁移。发生新提交后禁止用升级前备份覆盖现有账本；回退须保留最新任务事实并做兼容迁移。

容量决定还保留最近的 `lastRelease` / `lastRestore`（版本、原因、证据哈希、时间），同次原子保存；这些是固定大小的最新依据，不在共享账本追加无限历史数组。全局票据仅保留活跃派发范围，历史身份仍在原任务和批次记录中。

本次实施仅做隔离离线验收；不据此声称真实网络、供应商容量或收费生成已通过。真实性、性能样本和未验收项见本次实施报告。
