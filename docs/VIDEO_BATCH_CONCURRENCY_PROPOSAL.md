# 视频分段持续补位：四并发实施方案

状态：2026-09-21 已完成产品代码、CLI 和三个项目内 Skill 接入。本文保留设计依据；实际命令见 [README](../README.md#四并发持续补位)，实际离线验收结果和未真实验证项见 [实施报告](VIDEO_BATCH_CONCURRENCY_IMPLEMENTATION_REPORT.md)。未发起本次真实付费并发验收。

交给 ts1 的实施任务书、CLI 参数定稿、执行边界和验收指令见 [VIDEO_BATCH_CONCURRENCY_TS1_HANDOFF.md](./VIDEO_BATCH_CONCURRENCY_TS1_HANDOFF.md)。本文第7节为接口概要，具体格式以该任务书为准。

## 1. 推荐实现

在现有 metasocli 内增加一个可恢复的批次调度器。一个本地 CLI 调度进程管理用户本次授权范围内的全部生成段，最多保留4个占用生成额度的任务。有任务在服务端终结，便按原顺序补入下一段；下载由独立的小队列处理。继续采用 Node.js、TypeScript、Zod 和原子文件记录，不增加数据库、依赖、网页后台或常驻服务。

4 是本方案的本地保守上限，可选择1—4；不是本次已经查证的供应商账户限制。实施真实验收前只读核对账户实际限制，并遵守更低的限制。这里管理的是尚未终结的远端视频任务数量，不只是同时打开的 HTTP 请求数。

## 2. 用户操作与队列范围

- 用户说“生成这三集全部视频”：取得这三集已准备好的原始集计划，按用户指定集顺序及计划内段落顺序冻结一个批次；不依赖文件名的字典排序。
- 用户说“只生成第一集第3—6段”：批次仅包含这些段。来源、图序、旁白及其范围、模型、时长、分辨率保持计划原值；实际请求必须 context_ir_enabled:true。
- 完整原文和所有所需资产先准备、检查好，再进入视频批次。批次运行不改提示词或重新生图。
- 准备批次不收费；已明确授权该范围按当前默认 H3＋内联 IR 生成时直接执行，不额外要求固定授权口令、不逐段重复询问。
- 默认复用同请求的已完成结果，已提交任务接续原 ID，只补尚未提交的段。不要通过删除任务、改提示词或改哈希来重做已成功任务；成功任务的明确重做能力是独立范围，不借并发改造暗中加入。

开始前展示总段数、可复用数、已在生成数、本次将新建数和并发上限。每项固定 order、projectId、episodeId、segmentId、planId、planHash、requestHash、inputHash；同一项不能因完成顺序变化而改号。

## 3. 运行规则

1. 先核对本批次以及已登记的活动任务，接回原任务 ID，再计算剩余可用名额。
2. 在同一个短临界区内，按队列顺序为最早的待提交项预留空位并持久化提交意图。首次最多预留4项，然后并行发送它们各自的创建请求。
3. 创建返回后立即持久化 task_id。创建请求结束不释放生成名额；queued、running 和内联 IR 处理期间都继续占位。
4. 独立、有界地查询每个已知 task_id。确认 succeeded 且身份/响应校验通过、状态已保存后释放一个生成名额，马上派发下一项；同时将该结果放入下载队列。
5. 下载最多2个并行，不占视频生成的4个名额。下载慢或失败不能堵住全部补位，也不能重新创建视频；恢复下载时重新查询原 task_id 获得有效地址。
6. 剩余段不足4个时只处理剩余段。所有项都完成生成且文件验证、下载完成后，批次才标记完成。存在失败、缺失输出或未知任务时如实标记部分失败或需要处理。

例如最先派发第1、2、3、4段；第3段先完成就补第5段，此时活动项为1、2、4、5；随后第1段完成就补第6段，此时活动项为2、4、5、6。无需等待整组4段全部完成。

“补位及时”指下次查询确认完成后立即调度；轮询间隔建议5秒，不能承诺远端完成的同一毫秒已被本地获知。

## 4. 必须调整的现有代码

现有 generate 是逐段 await submit，再 await resume。submit、resume 都长期持有项目锁；resume 连轮询等待和下载也在锁内。直接用 Promise.all 调用四次现有函数会遇到 LOCK_BUSY。另一处约束是 readJob 会将磁盘上的 submitting 保守解释为 submit_unknown，checkSubmissionConflicts 又禁止其他提交；并发实现必须明确区分仍在受控执行的请求和真正失联的请求。

### 提交拆分

将现有 submit 的内部实现拆为三个阶段，现有单段公开接口继续复用它们：

1. 准备：短项目锁内校验计划、原文、素材和重复任务，预留共享名额、写操作意图与提交归属。
2. 请求：释放项目锁后进行一次 create；多项可同时进行网络等待。
3. 落盘：重新取得短项目锁和对应操作的写权限，尽早保存远端回执及 Job 状态，再更新批次索引。

提交归属须有可验证的进程/运行 token 和原子记录。只有当前调度器仍确知在执行的提交可视为 submitting；进程死亡、回执丢失、所有权不明时仍转入 submit_unknown。恢复时不能仅因为 token 或时间过期就认为远端没有任务。不要简单删除现有未知状态检查。

### 查询与下载拆分

提取单次查询与状态合并能力，网络请求和轮询 sleep 不持项目锁。合并结果时重新读取任务、校验身份和版本，防止旧查询结果覆盖新的终态。下载按 operationId 独占，网络传输与文件验证不占项目锁；最终回执及输出提交使用短锁。

原 submit/resume/download 的单段行为、任务 ID 恢复、回执、输出命名和验证继续保留。调度器不另外实现一套 Metaso 请求适配器。

### 锁和共享额度

采用“共享调度归属锁 + 短项目写锁 + 单任务下载锁”。所有状态写入采用固定顺序，在同一进程内先按故事根串行化短写入，避免4个异步回调互相触发 LOCK_BUSY。任何环节都不得一边持项目锁等待网络，一边申请共享锁。

首版同一 metasocli 安装仅允许一个活跃批次调度器；其他项目的批次等待该调度器释放，不做复杂的跨批次混排。所有新版公开创建入口，包括 generate 和 submit-only，都参与共享额度检查，不能让另一个项目再额外创建4个任务。已知旧任务在启用前登记并计入；网页、旧版本、其他电脑和未登记的外部调用不在本地调度器控制内，不能承诺账户全局绝对不超限。

独立运行记录使用 metasocli 自己的命名空间，默认可位于 `%USERPROFILE%\.metasocli-runtime`。开发和测试通过注入路径放在 E:\metasocli 或测试临时目录，不覆盖旧运行目录、配置、Skill或安装。

### 创建响应超时

mttest2 的真实第三段在客户端30秒超时后远端仍生成成功。因此建议为创建请求单独设置120秒响应期限，查询维持30秒，并保留有界取消。延长等待不是重试策略，也不能保证不再出现未知结果；120秒仍无完整回执时按 submit_unknown 处理。

## 5. 持久化与恢复

新增 `.metasocli/batches/<batchId>/plan.json` 保存不可变批次范围和顺序；run.json 保存运行进度、授权范围对应的批次哈希、各项 operationId 和运行归属。任务本身仍以 `.metasocli/jobs` 与 receipts 为真相，批次索引可以由它们恢复，不能因为索引缺失就再次生成。

共享运行目录保存提交预留和活动任务索引，不保存 API Key、认证头、媒体 Base64 或完整签名链接。名额的生命周期与远端任务相连，而非进程存活时间；CLI 退出不能直接清空名额。先保存提交意图再发请求；先保存可信任务/终态回执再释放名额。跨文件写入故障时宁可保留占位、执行核对，也不能释放后重发。

同一批次重复 run/resume 只取得同一批次并恢复原任务，不生成重复队列。恢复步骤为：读持久化预留 → 协调 Job/receipt → 查询已确认 task_id → 恢复未完成下载 → 在原授权范围内补尚未提交段。任何计划/素材变化阻止受影响的新提交，已接受任务仍按原 ID恢复。

原来的 resume --operation 永远只处理一个原任务。新增 batch resume 会继续原批次已授权但尚未提交的段，文档和输出须明确这种语义，不能与旧单任务恢复混淆。

CLI 退出后远端任务仍可能运行，本地补位及下载会暂停。恢复批次后继续；首版不承诺关机后自动运行。

## 6. 故障策略

| 情况 | 名额与后续动作 |
|---|---|
| 服务端 succeeded，身份及响应合法 | 保存状态后释放生成名额，补下一段；下载独立进行 |
| 服务端明确 failed/cancelled | 保存失败并释放名额，继续其他已授权段；不自动付费重做该段，最终报告失败项 |
| 创建超时、回包不完整、5xx或任务ID不明确 | 保留未知占位，停止本批次新提交；已确认任务继续查询/下载；找回ID后恢复 |
| 已知任务暂时查询失败 | 保留原名额、原ID，有界重试GET；其他已确认可推进项继续 |
| 无法识别的状态或身份冲突 | 不释放相应名额，保留证据，停止不安全的新提交 |
| 401/403/402 | 停止新提交并报告账号或余额问题；已接受任务不重复创建 |
| 429 | 遵守 Retry-After 暂停新提交；只有明确未受理且没有任何任务ID的拒绝，才按批次中预先确定的有限退避策略重试该待提交项；保留每次尝试记录。响应含矛盾信息按未知处理 |
| 下载失败或本地断网 | 不再生成视频；按原ID恢复下载，失败输出不会冒充完整交付 |
| 进程崩溃或多进程竞争 | 依据归属、预留、Job及receipt核对；死进程不等于远端任务消失；竞争者不得另建相同任务 |

计入4个名额的至少包含已预留待发送、submitting、queued、running，以及尚不能排除远端活动的未知任务。不能只计算 running，也不能在收到 task_id 时立即释放名额。429的自动退避次数和累计等待预算必须有上限，并在批次运行记录中固定；不能自动重试其他失败。

## 7. 命令与 Skill 接入（实现接口以任务书及 README 为准）

```text
batch plan --root <story> --all-episodes --concurrency 4
batch plan --root <story> --episodes <按顺序列出的集ID> --concurrency 4
batch run --root <story> --batch <batchId> --confirm
batch status --root <story> --batch <batchId>
batch resume --root <story> --batch <batchId>
```

batch plan 根据选定原始集生成合法的 inline 计划并复用相同请求的任务/成片，支持限定段落的结构化清单；不自动选择历史 IR 副本集。已实现 `--episodes`、`--selection`、`--all-episodes` 三选一，定稿格式见任务书及 README。

剧本、成品提示词、旁白三个 Skill 均改为：整理原文和资产 → 核对选定范围 → 准备批次 → 已获生成授权后运行批次 → 汇总新建、复用、失败和输出。用户继续用“生成这三集全部视频”“跑完这些段”即可，不要求手动凑4段或逐段发命令。图片Skill无需改生成逻辑。

## 8. 代码范围、测试与交付顺序

建议新增 contracts/batch.ts、jobs/batch-store.ts、jobs/batch.ts 和共享调度协调模块。调整 cli/main.ts、jobs/submit.ts、jobs/resume.ts、jobs/store.ts、jobs/submission-guard.ts、jobs/video.ts、storage/locking.ts；client.ts仅为创建/查询提供独立超时。保留 H3 请求构造、原文、时长、参考图、旁白适配及现有任务记录兼容，不改默认 true。

实施顺序：

1. 保存现有源码及旧项目隔离基线，梳理新增运行归属；先完成单段提交/查询/下载的短锁改造，保持旧测试。
2. 建立不可变批次及共享预留，完成四任务持续补位与独立下载队列。
3. 接入 CLI 和三个 Skill，保留明确授权范围、旧任务恢复及公共入口的额度约束。
4. 使用假客户端与隔离进程完成下列离线测试，再构建；没有新的付费授权时不发真实验收请求。

必验场景：

- 三集16段顺序冻结；任意乱序完成时，下一提交始终取最早的待提交项。
- 4个创建请求通过屏障确实可同时在途；第3段先结束时第5段在其他3段未结束前开始，整个轨迹中占位数始终不超过4。
- API创建已返回ID但远端仍queued/running时不能补入第5段。
- 下载故意变慢或失败时仍继续补位；下载并发有上限，输出位置与集段编号正确。
- 两个CLI或两个项目同时运行，以及 generate/submit-only 与批次交叉，不能绕过共享上限或产生重复任务。
- 提交意图后、创建已发后、回执已写后、终态保存前后、释放名额前后、下载改名前后分别中断，恢复不重建已接受任务。
- 同批次多项submitting仍可正常并发；真正submit_unknown出现后不补新任务，已确认项继续完成。
- 429明确拒绝、429含任务ID、401/402/403、5xx、查询未知、素材变化、记录篡改、旧成片复用、返回身份冲突。
- 每次视频请求仍为context_ir_enabled:true；正文、图片/音频内容和有序绑定与原计划一致。
- 所有历史单段、独立IR、回执恢复、进程故障和隔离测试继续通过，E:\libcli及旧安装不变。

完成离线验收后再在用户明确授权范围内验证真实并发上限和限流行为。并发验收需要多个独立任务，不能把此前的一次付费测试授权扩大使用。交付时分别报告已实现、离线通过、真实验收及尚未验证的项目。
