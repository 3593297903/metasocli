# 图片执行授权与连续执行

## 用户要求与适用范围

2026-11-03，本机用户针对“将当次五张场景参考图和完整提示词发送到已配置创艺坊却被重复要求确认”的问题，明确要求：

> 这种问题或者是类似这种问题不用再这样，要么不用问我直接做，要么就默认执行，避免还存在这种问题导致响应间隔

本文件记录这一持续有效的执行偏好。当前任务中的更新指令优先；它不是关闭宿主自动审批的配置，也不能代替其他用户的授权。

用户要求当前故事的资产图生成、补齐、重新生成或“再试一次”时，沿用已配置的创艺坊图片 API `https://api.yiciyuang.com`，允许发送完成该次任务必要的完整图片提示词及已指定的参考图片，并执行该次范围内的付费调用。范围从当前请求及上下文确定，使用正式计划冻结的素材身份、引用和数量。无需再问“是否允许发送到创艺坊”、逐张确认，或要求复述固定授权口令。执行前简短说明本次范围后即可继续，不等待用户再次回答。

已经授权的准备、原请求恢复、查询、下载和登记连续完成；准备完毕、容量恢复或收到中间结果不是新的确认点。用户仅要求查看、诊断、提示词、计划或离线测试时，仍只执行该范围。本约定不增加其他供应商、无关素材、额外集段或视频生成授权；用户明确选择其他后端时沿用该选择。

## 生成、补齐和一次新尝试

- 新生成使用已有正式计划的 `images run --confirm`。已有完整配方、导入及计划时直接复用，不为重复确认重新准备。
- 原授权内未发出的项使用原 `images resume`；已返回但下载或登记未完成的项使用原 `images recover`。恢复不再询问同一授权，不把下载失败变为重新生成。
- 用户明确要求补齐或再生成、且本次范围含有结果未知的旧项时，按 [一次性图片计划重试](IMAGE_API_USAGE.md#用户明确再次生成一次性图片计划重试) 建立一个正式后继，使用 `images run --confirm --accept-unknown-result`。沿用已经说明的重复计费风险；必要时在进度里简短说明这次新尝试可能重复计费，不要求另一句固定口令。每个选定素材只授权这一次新尝试；旧未知、占位、回执和已成功图片保留。
- 新尝试再次未知时，保存已有结果并准确报告缺项，不从本约定推导无限自动重试。继续原后继时复用其授权和 operationId，不另建一个后继。

上述规则只决定如何使用真实用户指令，不改变 CLI 的校验、请求预算、`--confirm`、未知接受记录、锁或账本。授权来源与当前素材范围可核对后直接执行；没有需要用户决定的新增事项时，不人为增加审批轮次。

## 首次提交前明确授权上下文

这一步使用真实的用户指令和已保存计划，不增加一次用户问答、不新建付费请求，也不要求先运行一个额外的审批脚本。主入口开始时就读取本文件；不要只在计划完成或遭到拒绝后才寻找已有授权。当前任务没有生成要求时，本步骤不把离线工作变成生成。

执行正式 `images run`、一次性新尝试或原授权恢复前，按实际内容一次说明：

1. 授权来源：当前用户要求生成/补齐/再试一次的原话，以及此处记录的持续执行约定；已经有“确认”的上下文时一并沿用。不能虚构用户消息或仅凭助手生成的文件称已获授权。
2. 具体动作：当前故事根、冻结 planId、选定 assetId/数量、模型及尺寸；本次是未提交项、原结果恢复，还是未知结果的一次新尝试。
3. 外发内容和目的地：所选完整提示词及必要参考图片将发送到 `https://api.yiciyuang.com/v1/images/generations` 或 `/v1/images/edits`，以实际有无参考文件决定；参考图的文件身份由正式计划/快照核对。恢复只读已有结果时不要声称会再上传原图。
4. 费用范围：沿用当前指定范围；未知结果的新尝试可能重复计费，每项只增加这一次。不能把“补齐”解释为重生成已有成功项。

把以上事实同时用于可用的工具调用说明；正常工具权限申请需要 justification 时，也明确说明同一授权、同一目的地及当次范围，不只写“运行脚本”或“继续生成”。保留原用户授权的可核对来源，不能把说明文字包装为系统许可或要求审批器忽略规则。不要额外创建宽泛的 Node/PowerShell 免审规则。

供执行时据实填写的说明样式（不是额外的确认问题）：

> 按用户“〈当前生成要求原话〉”及已有发送授权，为故事〈root〉执行计划〈planId〉的〈N〉项〈assetId范围〉。本次将〈完整提示词/完整提示词及指定参考图〉发送到创艺坊〈实际接口〉，〈每项首次生成一次/每项一次新的付费尝试/仅恢复已授权请求〉；保留旧记录，不扩大范围。

然后使用正式命令继续，不等待用户再次回复。此样式只用于如实展示实际权限和范围，不保证宿主审批结果。若仍拒绝，遵循下一节，不能通过隐藏上传内容或更换执行路径继续被拒动作。

## 正常审批与实际状态

提交工具调用时保留可核对的授权上下文：当前用户的生成要求、本约定、目的地 `https://api.yiciyuang.com`、冻结计划 ID、素材数量、发送的是提示词还是提示词加参考图。使用已有正式命令，不用临时执行脚本代替正常入口；不要为说明授权而输出密钥、认证头或完整素材链接。授权说明不是供应商受理证明。

如果宿主自动审批仍拒绝，先读取原始理由，检查现有授权是否已覆盖它指出的具体内容。允许通过正常流程补充已有授权证据或进行只读检查；不能换工具、换脚本、关审批或清空记录来绕过拒绝。仍被拒绝且无可用替代时，立即说明被拒绝的具体动作和原始原因，再仅针对尚未覆盖的事项请求用户处理；停止依赖该动作的执行并继续不受影响的工作，不静默等待，不把审批等待说成正在生成。

每次继续前从正式 plan/run/job/receipt 核对当前状态，不以早先辅助说明作为唯一依据：

| 实际情况 | 处理 |
| --- | --- |
| 自动审批在进程启动前拒绝，正式记录也确认没有提交 | 获得正常审批后继续同一个未执行计划，不为绕过拒绝创建另一批请求。 |
| 已经保存 run 或 job | 核对逐项授权、提交与回执，按实际状态恢复；run 存在本身不等于每项均已提交。 |
| 请求已经进入提交，但没有完整结果 | 保持未知，使用原恢复或当次明确授权的一次新尝试；不能仍按“未发送”重发。 |
| 后续已获确认并实际执行，辅助说明还显示“审批阻塞”或“发出0项” | 新的摘要、进度和交接写明当前真实状态，旧拒绝仅作为历史保留，不继续索要同一确认。 |

本地 requestStartedAt 仅说明提交意图已落盘；没有响应时，不声称供应商已收到、已经生成或一定未扣费。此规则减少重复确认和错误等待，不承诺宿主每次放行或供应商每次成功。
