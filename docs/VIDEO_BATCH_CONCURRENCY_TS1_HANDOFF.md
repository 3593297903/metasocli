### 二、必须交付的行为

1. 将用户选定范围内的所有待生成段组成一个不可变批次，按指定集顺序、原计划段落顺序派发。数量不限于8段。默认最多4个占用生成名额的任务，并允许设置1—4。
2. 首次有足够任务时，4个创建请求能够同时在途。返回 task_id 不释放名额；只有服务端终态经身份校验、持久化确认后才释放。任意一段终结后立即调度下一待提交段，无须等待整组结束。
3. 下载独立并发，默认最多2个。生成完成后即可补位；下载失败只恢复下载，不能重新创建视频。输出按原集、段落及 operationId 保存，完成顺序不得改变归属。
4. 保存批次、授权范围、共享预留、任务和回执。重复运行及中断恢复必须接回原 task_id，复用同请求的合格成片，只创建本批次已授权而未提交的段。
5. 创建结果未知时保留占位、停止新增，已知任务继续查询和下载。明确失败的任务记录失败并释放名额，继续其余段，不自动付费重做。429只有明确未受理且无 task_id 才允许有界退避重试；超时、5xx、矛盾回包不能当作安全重试依据。
6. 将网络等待移出项目锁，采用短状态写锁、可验证的提交归属和单任务下载锁。必须正确区分仍在执行的 submitting 与真正失联的 submit_unknown，保留防重复创建和原有恢复保护。
7. 首版一个本地安装只运行一个活跃批次调度器，其他批次等待。所有新版视频创建入口，包括普通 generate 和 submit-only，共用预留与上限；不能各自再开4个任务。未知占位不能因进程退出被清空。说明本地协调无法控制网页、旧程序、其他电脑的外部调用。

### 三、CLI 接口定稿

以下接口需要实现并测试后才可运行；使用本地入口 `node E:\metasocli\dist\cli\main.js`，不安装或覆盖全局命令：

```text
batch plan --root <story> --episodes <逗号分隔的有序集ID> [--concurrency 4]
batch plan --root <story> --selection <selection.json> [--concurrency 4]
batch plan --root <story> --all-episodes [--concurrency 4]
batch run --root <story> --batch <batchId> --confirm
batch status --root <story> --batch <batchId>
batch resume --root <story> --batch <batchId>
```

plan 的三种范围参数互斥。`--episodes` 按参数顺序选集，每集按现有计划顺序选全部段；`--all-episodes` 按故事清单顺序选择可确认的原始集，不自动纳入历史独立 IR 生成的副本。不能可靠区分时给出明确错误，让 Skill 改用显式范围，禁止按文件名猜测。

`--selection` 用于限定段落，也兼容“一个技术 episodeId 内包含多个剧情集”的已有项目。JSON v1 形状如下；集/段必须存在，数组决定顺序，不得重复项，不得按标题重新拆写故事：

```json
{
  "schemaVersion": 1,
  "episodes": [
    { "episodeId": "ep-1", "segmentIds": ["s1", "s2"] },
    { "episodeId": "ep-2", "segmentIds": ["s1"] }
  ]
}
```

batch plan 为所选范围创建或复用合法的 inline 计划，冻结哈希，输出总数、可复用数、活动数、待新建数和并发上限；不得付费。batch status 默认只读本地记录。batch run 的确认授权要绑定当前批次哈希并持久化；batch resume 只能在已有授权范围内恢复，未授权批次不得借 resume 创建任务。明确说明 batch resume 可以继续原已授权待提交段，而旧 resume --operation 永不创建任务。

若真实业务结构要求微调内部数据字段，ts1 自行作最小调整并记录理由；最终 README、CLI help、Skill 示例和测试必须一致，不能留下占位接口或仍须下一任务决定的参数格式。
