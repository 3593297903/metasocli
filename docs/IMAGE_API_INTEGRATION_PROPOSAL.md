# GPT Image 2.5 图片 API 全量提交实施方案

修订日期：2026-09-24。状态：待实施方案，下面新增的命令、模块、状态和配置均未实现。本次只修订方案，不代表已接入、已绑定图片 API Key 或已完成真实生图验收。

本版按用户明确要求取代 2026-09-23 的图片“四并发、完成一个补下一个”建议。新目标是：完整准备本次范围的图片提示词，将全部输入已就绪的图片请求集中发出，分别接收、保存和登记结果。视频原有四并发保持不变。

依据：[已核验的接口与代码分析](IMAGE_API_INTEGRATION_ANALYSIS.md)、当前资产/计划/任务/锁代码，以及 2026-09-24 再次只读核验的[供应商专属文档](https://newapi.yiciyuang.com/docs/exclusive-gpt-image-2)。通用接口页面与模型详情存在示例不一致，以专属文档作为暂定契约，真实验收后再标记兼容。

## 1. 实施目标与范围

保留当前完整素材分析、资产 ID、逐段引用、人物/场景/道具/首帧模板和完整图片提示词。图片 Skill 增加一个可明确选择的 API 执行后端：创艺坊 gpt-image-2.5。

一次选择多集或多段所需资产，复用准确 ready 资产，只生成必需且缺失的图片。200 份独立且输入已就绪的缺失配方建立 200 个独立任务，每个请求 n=1；程序集中启动这 200 次 HTTP 调用，不以任何一张生成完成作为提交其他独立图片的条件。结果乱序返回，按各自本地任务身份保存。图片下载、技术检查和登记完成后，沿用现有 H3 视频计划及四并发流程。

必须区分的三个边界：

- 当前专属文档的 prompt 是单个字符串，n 是同一提示词的出图张数，没有展示“一个请求接收 200 个不同提示词”的批量契约。因此第一版落实为 200 个独立请求集中发起，不发送 prompt 数组，不设置 n=200，也不虚构 /batch 接口。
- 当前文档列出直接返回 data 中的图片 URL/Base64，没有展示可凭 task_id 轮询的异步创建协议。客户端要维持这些 HTTP 请求直到逐项返回；不能承诺关闭进程后随时再查询图片。
- 集中发起不等于服务端全部受理，更不等于 200 张同时开始推理。账户并发、每分钟请求数、余额、网关最长连接时间和服务端排队规则仍待确认。若已知额度小于本次集中请求数，应在付费前明确报告，不静默改回四并发补位。尚未确认的容量不能写成已验证支持。

实现 generations 与带依赖图片的 edits，不把已有图片依赖降级为文字。旁白录音不进入图片任务。

继续使用 Node.js/TypeScript/Zod 和文件持久化。不新增 SDK、数据库、消息队列、常驻服务或通用插件框架；不自建 New API 网关。不修改 E:\libcli、旧安装、旧 Skill、旧运行目录及登录状态，不推送 GitHub。

## 2. 业务流程

1. Skill 完整分析本次范围，整理逐集图片请求和逐段引用；跨集共享资产保持同一 ID。
2. 按现有完整模板生成配方，验证 request/recipe 与草稿一致，完成该范围的 import。
3. CLI 创建图片计划，按需要的资产及依赖闭包去重，列明复用、缺失、首轮可立即提交、等待参考图、外部阻塞、预计请求数、模型和尺寸；提交模式固定为 all-ready。
4. 获得该供应商及该范围的生成授权后运行；一次授权覆盖冻结的资产范围，不逐图再询问。
5. 将当前全部可提交项集中发出；每张图的本地 operationId 始终绑定自己的 assetId 和请求内容。不得等待某个生成结果才启动另一个已就绪项。
6. 每个响应独立接收，尽早持久化可恢复回执；下载和解码受独立并发限制，校验后排队登记为本地资产。某张参考图登记完成后，立即集中启动由它解锁的全部就绪项，不等待其他无关图片。
7. 输出逐项结果和可打开的图片索引，继续保持首次结果保存展示，不增加自动审美检查、OCR 评分或自动重画。
8. 所选范围的必要图片全部 ready 后，创建新的 H3 视频计划。视频是否提交继续服从原有视频授权范围，context_ir_enabled:true 与旁白绑定保持原有行为。

第一版按一个所选范围先完成图片阶段，再进入视频新提交阶段。同一故事不交叉运行图片准备和视频新提交，避免全局 revision 变化使视频批次过期。已有视频 task_id 的查询、下载和恢复可以继续。

如果 200 项都不依赖尚未生成的图片，首轮就是 200 项。如果其中 40 张首帧需要先生成的人物/场景图，计划明确显示“160 项可先发、40 项等输入”。这种等待由真实参考图依赖造成，不能删掉依赖或仅用文字代替参考图来伪装全部已提交。

## 4. 图片规格

配置分别定义 boardSize 与 firstFrameSize；不能从视频段的 ratio 无条件推导所有图片尺寸。

- 人物/场景/道具：保留横向设计板布局。对没有既定像素要求的新资产，首轮兼容默认可用专属文档列出的 1920x1088。
- 竖向首帧：按实际镜头意图，文档列出的竖屏映射为 1088x1920；其他意图必须显式指定已核实的尺寸。
- 这两个尺寸在供应商文档归入其 1K 映射，不得标成 2K/4K，也不是数学上精确 16:9/9:16。
- 原提示词明确要求更高规格时，计划必须标明配置冲突，不能静默降级。2K/4K 可通过显式、经核实的 size 配置启用，不能猜造未列出的比例映射。
- 保存 requestedSize 与实际 width/height，不能靠提示词中的“4K”认定输出尺寸。

复用现有 inspectImage：PNG/JPEG/WebP，单图至多 30 MiB，宽高 256~5760，宽高比 0.4~2.5。图片就绪后还要按实际段落组合检查 H3 64 MiB 请求上限、最多九张图及旁白开销。第一版不静默压缩、裁图或删引用；超限应定位资产和段落。

## 6. 计划、身份和去重

ImagePlan 不使用全局 revision 相等作为执行前提。可以保留创建时 revision 作为诊断信息，但任务有效性由以下内容决定：

- projectId、选中的集/段及资产 ID/引用关系；
- 每项的 recipeHash、原始提示词哈希、kind、依赖 ID 顺序；
- 固化后的 provider、model、quality、size、n、返回格式与执行配置；
- 目标资产原有 media 哈希或“原来缺失”；
- 已有依赖图片的真实哈希，或同计划中负责生成该依赖的上游项身份。

待生成的依赖在计划时还没有图片哈希，不能伪造。计划冻结其上游生产项与配方，实际提交前将已经登记的依赖结果解析为具体文件/哈希，保存到 Job 的有效输入记录，再计算 requestHash/inputHash。保持计划不可变，不在每张完成后改写 planHash。

优先沿用用户选定集/段顺序及素材首次使用顺序；在依赖允许的前提下做稳定拓扑排序。只选择该范围真正需要的资产及依赖闭包，排除 narration 和未使用可选项。跨集同 ID 去重。

已有 ready 文件按当前规则复用，不因启用 2.5 而自动重画。缺失但已有已完成结果的，先恢复文件/登记。当前未决任务必须先恢复，不为它另建一个重复付费任务。被其他任务或用户替换的目标产生明确冲突，保留返回图片，不覆盖新选择。

原 recipeHash 保持原语义；新增的执行哈希包括供应商、参数及真实参考图片哈希，密钥不写入记录。原始提示词不缩写、不二次优化、不静默截断。供应商 revised_prompt 单独记录，不覆盖 recipe.prompt。

计划使用逐项 ID、哈希和输入文件引用，不把 200 份长提示词、参考图或 Base64 全部复制进一个 JSON。原有故事/结构化文件的 8 MiB 限制仍有效：预检超限就定位报告，不通过截断正文绕过；必要的执行输入按任务独立落盘，保持计划不可变。

## 7. 全量启动、接收与阶段协调

第一版每个图片 quotaGroup 同时只允许一个活动运行进程，进程内可集中发起整个就绪集合的请求，另设下载/解码限制和单故事登记队列。其他项目可查看状态、恢复已返回结果；另一个新批次不得无感叠加。这个互斥限制的是同时运行的批次，不是将一个批次限成四个生图请求。账本记录请求和归属，不实现“生成名额释放后补位”。

执行顺序：

1. 一次完成选中范围的全部配方、映射、规格和已有输入预检；冻结计划及授权，登记所有任务为 prepared/等待依赖。相同参考文件按哈希复用受管理的输入快照，避免每项重建全项目视频请求。
2. 获取图片运行归属和同故事图片阶段归属，核对是否存在未决请求、同资产占用或已知额度不足。在项目短写事务中保存任务预留；网络等待不持项目锁。
3. 对当前所有就绪项启动提交过程：逐项在短锁内持久化 submitting 意图，锁外立即发起 HTTP，然后启动下一项。允许必要的本地写盘耗时，但不能 await 上一项的远端生成结果，也不能固定每隔 15 秒才发送。
4. 每项发出时立即绑定自己的接收/错误处理器，最后汇总全部已启动项的 settled 结果。不能因一个 Promise 拒绝就停止收集其他已经发出的请求，也不能等所有请求都返回后才保存第一项结果。
5. 收到响应体就按本任务路径流式、有界落盘并保存完整性证据，再进行有界解析；得到可用图片地址后单独下载。图片返回慢、下载慢或登记忙，不得成为其他已就绪任务尚未发出的理由。
6. 某个依赖的图片下载、检查和正式登记完成后，找出刚刚具备全部输入的后续任务，立即集中启动。不存在“生成槽位满了”等待；只保留真实依赖、错误停止和明确的账户限制。
7. 短锁内条件登记：检查任务归属、recipeHash、目标 media 未被替换、依赖哈希仍匹配，再原子写入。已登记字节与持久化结果一致时只修复任务状态，不重复生成、不无故增加 revision。

prepared 与 submitting 必须分开：不能为集中启动而预先将 200 项全标为“已发送”。崩溃后，有提交意图却没有完整结果的项可能为 unknown；仍处于 prepared、且协议保证尚未进入发送步骤的项才可继续提交。真实发送与持久化之间不可消除的窗口必须保守处理。

HTTP 层也必须支持本轮请求数：不得在 fetch/代理连接池中隐藏一个 4 或 10 的串行瓶颈。用本地 HTTP 模拟服务验证完整请求体已实际到达的数量；仅证明创建了 200 个 Promise 不算通过。客户端只能记录实际启动/传输时点，不能将其命名为服务端已受理时间。

“全量”不要求所有请求落在同一毫秒，也不要求等到全部发完才读已到达的响应。可靠目标是：独立请求之间不存在等待生成完成的依赖，按本机传输与持久化能力尽快启动全部。

登记器本身会获取项目锁；实现不能在外部持有同一个非重入锁再调用原登记器。需将条件检查与实际登记置于同一短写事务，或以清楚的内部 locked helper 复用，不能“锁外检查然后直接覆盖”。

项目图片阶段归属需持久化。图片启动和视频新提交在同一项目短锁下检查互斥状态，避免两个任务同时起跑。不能同时持有图片和视频的共享协调锁；各自锁顺序保持共享账本在前、项目短写在后。图片阶段进程退出后可释放本机执行租约，但已发出且结果未知的请求不能按超时从账本自动清掉。旧进程的存活、身份与接收归属必须验证，不能仅因心跳过期就同时启动第二个接收/提交进程。

常规 run 是一个随批次结束而退出的 CLI 进程，不需要常驻 Web 服务。本地运行期间持续接收状态；如由宿主托管后台进程，必须保存 PID/进程身份、日志和退出状态，不能仅显示“已启动”就当作生成完成。关闭电脑、杀掉进程或断网后，未收回的同步请求无法凭本地 operationId 向供应商查询。

## 8. 请求与响应实现

无依赖图片：POST /v1/images/generations，JSON，顶层 model/prompt/quality/size/n/response_format。

有依赖图片：POST /v1/images/edits，使用独立适配的 multipart/form-data；单图 image，多图 images。以供应商实际验收的文件字段编码为准，保留顺序；FormData 自动生成 Content-Type boundary，不手写错误边界。参考图来自受管理的真实文件，不自动上传到其他存储服务。

请求 model 固定为该计划的 gpt-image-2.5；无静默模型切换，无原生生图自动兜底。若未来增加别名，另行明确配置，不通过重试随机切换。

默认请求 URL 结果，客户端也可解析有界 Base64。n=1 时要求一个可辨识结果，额外/空数组等异常原样留证并进入需要处理状态，不静默挑选另一项。区分 HTTP 状态、业务错误、响应契约错误和图片技术检查失败。

图片响应采用独立字节上限：例如单份 JSON 响应最多 45 MiB、解码图片最多 30 MiB；不要复用视频 1 MiB 响应限制。原有 writeJson 上限 8 MiB，所以 Base64/图片二进制不得塞进任务 JSON，应单独保存并以文件哈希引用。

200 个请求会同时持有连接，但不能同时在内存拼接 200 份最大响应。响应读取器应以有界缓冲写各自临时文件，完整接收、flush、哈希和原子完成标记后进入解析队列。首次保存响应不能等两个下载槽位空闲才开始。受管理的 multipart 参考图片同样避免为所有请求复制大 Buffer；采用受控的文件输入，保留真实内容哈希。

启动前预检可用磁盘及本批保守空间需求；运行时限制单项与总体临时存储。存储失败要保留已有完整结果并停止尚未发出的任务，不能静默丢弃响应。部分响应与完整回执必须有明确区分，恢复不能将半个 JSON 当作生成失败后重发。技术校验后的文件及时进入正式结果路径，避免无限保留重复大文件；恢复仍需的文件不自动删除。

URL 结果的真实地址要在本地受保护的恢复记录中保存；公开日志使用脱敏版本。下载使用有界读取、不转发 API Key；第一版沿用安全 HTTPS 与拒绝不明确重定向规则，若真实 CDN 必需重定向，再加入明确验证与测试，不直接全放开。

图片保存为独立文件后，以 file 模式登记，不以供应商临时 URL 作为后续 H3 的默认引用方式。保留 usage、revised_prompt、供应商请求追踪头（如果确有返回）及请求/响应哈希，不凭空构造 task_id 或实际模型证据。

## 9. 状态与恢复

正常状态：prepared → submitting → response_saved → received → downloaded → registered。另有 waiting_dependency、reused、blocked、rejected/failed、submit_unknown、superseded；具体枚举可合并，但含义不能混淆。response_saved 表示完整响应体已保存，尚未完成结果契约校验；HTTP 200 本身不等于 received 或成功。

| 情形 | 必须执行的行为 |
| --- | --- |
| 尚未发送 | 在保存的授权范围内可继续提交 |
| 提交意图存在、进程丢失且无完整响应 | submit_unknown，不重新 POST，不清除未决记录 |
| 超时、断线、5xx 或损坏响应，无法证明未受理 | 记录未知并停止该额度组尚未发出的付费提交；已发出的其他请求继续接收、保存和下载，不集体取消 |
| 明确鉴权/余额错误 | 停止新提交，保留已经完成与在途任务 |
| 429 | 保存实际错误与 Retry-After，停止新提交；第一版不自动重发同一付费请求 |
| 完整响应已落盘、解析或写任务状态前中断 | 从该响应文件恢复解析，不重新生成；保留原始完整性与请求绑定证据 |
| 已收到有效图片 URL | 回执保存后可恢复下载，不重新生成 |
| 已下载、登记失败/锁忙 | 校验原文件并恢复登记 |
| 目标被用户替换 | 保存结果为 superseded/冲突，不能覆盖 |
| 依赖图片被换掉 | 尚未提交项阻塞；已返回项保存为冲突，不能自动冒充与新依赖匹配 |
| 结果地址过期且无本地文件 | 报告需恢复来源，不能悄悄重新生成 |

没有供应商查询/幂等保证，就不能承诺所有未知提交都能无人介入恢复。提供有记录的人工恢复入口：

- 找回该请求的真实结果后，可明确关联本地文件，验证哈希并记 recoveredManually，恢复登记及未决记录；
- 只有得到未受理/已终止的明确证据，才允许显式解除对应未知状态；
- 人工补一张别的图片、取消本地等待或经过一段时间，都不能自动证明远端请求未执行；
- 重试一个已确认拒绝/失败的请求应创建新的 attempt，关联 retryOf，并取得明确的新尝试授权；未解决的 unknown 不允许普通 retry 绕过。

第一版不实现自动付费重试。对只读下载/本地登记允许有界重试，且和生成尝试计数分开。

## 10. 拟定 CLI（尚不可直接执行）

```text
images auth-status
images plan --root <story> (--episodes <有序ID>|--selection <json>|--assets <有序ID>|--all-episodes)
            [--profile <json>] --submission-mode all-ready
images run --root <story> --plan <imagePlanId> --confirm
images status --root <story> [--plan <imagePlanId>]
images resume --root <story> --plan <imagePlanId>
images recover --root <story> --operation <id>
images attach-result --root <story> --operation <id> --file <image> --expected-sha256 <hash> --confirm-result-link
images resolve --root <story> --operation <id> --outcome not-created|failed --evidence <json> --confirm-resolution
images retry --root <story> --operation <id> --confirm
```

范围参数互斥。selection 复用现有 batch selection 的集/段格式；assets 可用于单独补图。计划报告引用与依赖闭包，显式排除旁白。

提交模式必须进入不可变计划及 planHash；run/resume 不允许临时换成其他模式。第一版只实现 all-ready，不额外实现四并发图片补位作为默认或隐式降级。下载并发写入 profile，不复用视频 --concurrency 参数。

- auth-status/plan/status 不发起付费请求；plan 无需密钥，auth-status 仅报告配置状态，不伪装远端认证。
- run 保存含 planHash、供应商、额度组、最大请求范围的授权索引，才开始付费调用。
- resume 可以继续该已授权计划尚未提交的项；帮助与输出必须明确这一点。不扩范围，不重新提交 unknown，不重复生成已返回或已登记项。
- recover 只恢复该任务已有结果的下载/登记，不发起生成。
- attach-result/resolve/retry 是明确的人工处理命令，不由普通 resume 偷偷调用。resolve 的证据应有来源与操作确认；不把一个任意 JSON 当作服务端事实。
- `--runtime-dir` 沿用现有测试入口；新的计划/命令不覆盖旧 video batch 命令含义。

正常用户仍用原来的两个成品提示词 Skill 或剧本 Skill。选择 API 后，Skill 自动完成图片 plan/run/status/recovery 的衔接，无需用户手动发 200 次命令。先收齐本次范围内的素材计划和提示词，再进入图片集中提交阶段；不要自动变回“分析一集、生成一集、再分析下一集”。已就绪共享资产照常复用。

## 11. 交接契约兼容

图片交接增加 api 模式，保留 built_in/not_run 与历史格式的解析。建议为 API 输出增加向后兼容的版本分支和独立 execution 记录，避免把新必填字段塞进旧记录。

`requestedModel` 必须来自真实请求；`reportedModel` 只能来自实际供应商响应。原有 requireExactModel=true 的不可独立核实限制不能因有请求 model 字段就被删除；如需要“禁止模型回退”，用明确的请求模型锁定语义表达。

三个上游入口与图片 Skill 一致选择后端。旁白入口仍单独登记音频，图片任务不包含 narration。切换默认后端不会自动改写旧配方、清空历史问题、覆盖用户图或重画 ready 图片。

## 12. 验收顺序与完成条件

### 离线验收

1. 请求契约：两种接口、完整提示词、模型/参数、依赖真实文件与顺序、URL/Base64 返回、无密钥泄漏。
2. 200 个独立模拟任务：本地模拟 HTTP 服务在收齐 200 个完整请求前不返回任何成功结果；客户端必须实际将全部 200 项发到服务端。测试设有截止时间，若隐藏串行/四并发就明确失败，不能死锁等待或仅断言 Promise 数量。
3. 第一张图登记后，余下任务仍可执行；全局 revision 改变不导致图片批次误失效。
4. 200 项乱序返回、同资产并发、共享资产重复使用、两个进程争用同一图片额度组、登记同刻完成、用户换图/依赖换图，均不串图、不重复提交、不覆盖新选择。
5. POST 前/后、回执前/后、下载前/后、登记前/后强制中断；unknown 不重新 POST，其他状态只恢复缺失步骤。
6. 429、401/402/403、5xx、HTTP 200 空结果、损坏 JSON/Base64、过大响应和图片、过期 URL、下载失败。
7. 并发登记无嵌套锁；图片/视频阶段冲突明确且无死锁，已有视频恢复仍可运行。
8. 旧 built_in 记录、已登记素材、视频四并发、旁白、H3 context_ir_enabled:true、路径与安装隔离回归通过。
9. 所选实际参考图组合通过 H3 请求构造；超限精确定位，不删引用、不改视频正文。
10. 混合依赖案例：无依赖项同时启动；某一人物参考图登记就绪时，只要对应首帧的所有输入齐备就马上提交该首帧，不等待无关慢图；实际上传图片哈希/顺序必须正确。
11. 其中一项 429、断线或响应持久化失败，不使其他已经发出的成功结果丢失；停止只影响尚未发出的项。resume 不重发任何 unknown。
12. 200 项响应可同时开始流入磁盘，有界解析/下载不拖成生图提交槽位；以可控小体积流验证 200 路接收，再用少量边界体积响应验证大小/内存/磁盘上限，避免测试本身耗尽机器资源。
13. 已知账户限额低于集中提交数时，在任何付费请求前报告不满足；未知限额如实显示待验证，不能在状态中伪造“供应商已接受 200 项”。

拟新增测试脚本 `test:image-api` 和 `test:image-api:process`，名称在实施时落实到 package.json。交付至少运行原有 build/test/test:image-skill/test:process 及新增图片进程故障测试，全部隔离运行，不需要真实 Key。不能把命令未加入 package.json 时写成已执行。

### 真实验收（需要后续明确授权）

先核实账户权限、并发/RPM/排队规则和连接超时，再按明确的次数/费用范围验收：一张文生图、一次带参考图编辑，再一次小规模全量提交；检查模型请求、真实返回、尺寸/格式、中文设计板表现、耗时、扣费和登记。文档没有说明的 prompt/参考图上限、并发和 URL 有效期保留为待验证项。小批成功不能证明 200 并发成功，离线 200 项通过也不能证明供应商容量。

如果供应商明确只允许更低的并发或 RPM，真正实现“200 项全部先交给服务端”需要供应商开放相应额度，或提供确实会先受理整批的异步/批量接口。核实新接口后单独适配；本地加排队、换成 Python、建代理转发层都不能把这个限制变没。本版不猜造批量/查询接口，也不在实现中自动切换提交模式。已明确的本次生成授权不逐图重复索取。

正常真实生图成功并不等于需要为故障验收反复付费；断线、回执丢失等以离线/进程测试为主。未授权前不提交图片或视频。

### 执行记录与交付

输出每张任务的 assetId、operationId、请求模型、尺寸、状态及以下时间：preparedAt、requestStartedAt、responseHeadersAt、responseSavedAt、receiptSavedAt、downloadCompletedAt、registeredAt；传输适配器能够可靠观测时另记 requestBodySentAt。依赖解锁事件记录触发的参考图和新启动的任务列表。客户端开始调用、请求体发完、收到响应头、完整结果落盘分别统计，不把本地启动时间当作供应商受理时间。

批次汇总列出 total/reused/waitingDependency/notStarted/started/inFlight/received/registered/rejected/unknown，区分“已启动 HTTP”与“已收到有效图片”。无需等全部成功才显示某张图片；结果索引按原资产顺序可查看，包含引用集/段与本地文件。

完成后交付：源码与构建、离线和进程测试结果、图片配置/连接说明、实际 CLI 帮助、更新后的 Skill、真实验收状态及未证实限制、旧 LibTV 边界检查。保持当前用户已有修改，不 reset、不覆盖旧安装、不推送。
